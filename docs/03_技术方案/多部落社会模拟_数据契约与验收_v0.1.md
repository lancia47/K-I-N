## 3. 数据所有权和知识权限

### 3.1 三类视图

| 视图 | 允许读取 | 禁止事项 |
|---|---|---|
| WorldCore 权威视图 | 真实库存、位置、成员记录、协议、伤势 | 让模型直接改值；把推测当事实 |
| 个体决策视图 | 自身状态、感知、记忆、公开或被告知的条款、自己所知的关系 | 对方私人库存、隐藏目的、全图位置 |
| 玩家界面视图 | 玩家已观察/获知的消息、公开回应、自身权限与承诺 | 默认展示全知派系图与所有关系分数 |

组织协调器只读取它获授权且已收到的信息，不读取全体成员的秘密目标。每个参与者对任务独立回应；协调器整合回应，不能伪造全体接受。

### 3.2 与已有字段兼容

保留 `history`、即时 `events`、`perceptions`、`beliefs`、`memories` 的职责分离。保留 `trust/fear/belong`，按既有路线扩展 `obligation/resentment/familiarity`，不擅自用旧理念文档中的另一套关系字段替换实际存档。

已有字段范围、ID 类型、时间单位以工作区核验为准。下面新对象名称是目标契约名，不是要求原样创建同名文件或覆盖现有结构。适配器应先映射已有实现，避免两个系统维护同一份库存或关系。

## 4. 最小对象契约

| 对象 | 必需字段或职责 | 生命周期要点 |
|---|---|---|
| Camp | 稳定 ID、位置、仓库引用、设施引用 | 居住地不等于组织 |
| Group | ID、类型、名称、成立记录、规则版本、状态 | 类型区分部落/家族/派系/联盟 |
| Membership | 人员 ID、组织 ID、接受记录、加入/离开时间、角色 | 允许多重身份；退出不删历史 |
| Mandate | 组织、持有人、授权动作、仓库、限额、期限、授予/撤销事件 | 人物与职位分开 |
| Proposal | 发起人、目标、条款版本、预算、资格快照、回应、截止时间 | 重大条款变化必须重新确认 |
| Commitment | 承诺者、承诺对象、动作、条件、期限、退出规则、状态 | 不能替他人作无限承诺 |
| TradeAgreement | 双方、代表与授权、货物、交付地点、时限、交付规则、状态 | 接受不等于实际交付 |
| DeliveryLeg | 协议、发出/接收方、应交数量、实交数量、货运引用 | 一笔协议可有两条交付腿 |
| Shipment | 所有者、保管人、货物批次、数量、位置、路线、状态 | 所有权与携带位置分离 |
| JointOperation | 类型、提议与授权、实际参加者、预算、目标、终止条件 | 非参与者不自动被动员 |
| Grievance | 提出者、被指对象、事件/传闻依据、诉求、回应 | 是可归属的主张，不是客观定罪 |
| RepairAgreement | 双方有效接受、赔偿/返还/担保条款、履行记录 | 不删除旧关系和记忆 |

Group 不自带全局“真实声誉”。关于个人或团体的判断保存在观察者的 Belief 中。正式成员身份、当事人对外声明和观察者认定分开表达。

## 5. 事件账本和消息投影

### 5.1 追加式事实

每个已结算事件需要稳定 `event_id`、模拟时间、类型、参与者、目标、位置、真实状态变化、规则版本及必要的前置事件引用。新发生的转述是新事件，不修改原事件的目击名单。

同一个事件可以产生不同的感知投影。只能先过滤可观察字段，再交给记忆和判断系统；不能把完整 Event 发给 NPC 后要求它“忽略隐藏字段”。

示意数据，仅用于解释契约：

```json
{
  "event_id": "demo:1042",
  "tick": 840,
  "type": "shipment_dispatched",
  "actor_id": "npc_carrier",
  "target_id": "camp_hill",
  "location_id": "camp_river",
  "agreement_id": "trade_07",
  "causal_parent_ids": ["demo:1038"],
  "state_changes": [
    {"kind": "cargo_location", "cargo_id": "cargo_31", "from": "store_river", "to": "npc_carrier"}
  ],
  "rule_version": "kin_intertribal_v0.1"
}
```

`causal_parent_ids` 表示实际执行依赖，例如某次发货依据已接受协议；它不是关于人物深层心理动机的证明。叙事推断要另标为解释，不能添加成权威因果事实。

### 5.2 新增事件目录

| 类别 | 建议类型 | 必须能证明的变化 |
|---|---|---|
| 交往 | contact_established、trade_proposed、trade_accepted | 谁获知了什么，谁接受了什么条款 |
| 运输 | cargo_reserved、shipment_dispatched、shipment_arrived | 预留、保管人、地点真实变化 |
| 交付 | trade_leg_received、trade_completed、shipment_overdue、cargo_lost | 数量、交付时间、未完成或损失 |
| 协作 | proposal_issued、proposal_response_recorded、task_committed、task_withdrawn | 可核验回应和个人承诺 |
| 组织 | membership_accepted、membership_left、group_established、group_dormant | 成员有效接受与后续变化 |
| 授权 | mandate_granted、mandate_revoked、leadership_changed | 授权范围及生效事件 |
| 冲突 | grievance_raised、operation_authorized、operation_started、operation_ended | 指控与授权、参加者、行动结果分离 |
| 修复 | repair_proposed、repair_accepted、restitution_delivered | 双方接受与真实返还 |

救援、搬运、伤害、死亡和肉类分配优先复用已有 `member_aided`、`carried_wounded`、`meat_shared` 等事件，不创建平行计账链。实际命名由 KIN-01 对照现有事件系统确定并写映射表。

## 6. 交易状态机和资源不变量

### 6.1 状态

```text
proposed → negotiating → accepted → reserved → in_transit → arrived → settled
```

分支包括 `rejected`、`cancelled`、`overdue`、`partial`、`failed`。`overdue` 不等于永久失败；解释、续约或迟到交付可继续推进，但原来的延误事实保留。`partial` 只有协议允许部分交付时才可正常结算，否则保持未完成并等待协商。

接受时验证代表授权、货物合法性、预算与时间。发货时再次验证资源与授权。到达时重新核验批次和实存数量，不能重复使用出发时的快照。

### 6.2 首个交换模式

双方各自运货到约定会合点。双方到齐且货物足额后，WorldCore 以一次事务改变两边所有权并标记交易完成。任何一方不足时不扣除另一方物资；可产生解释和重新协商。

远程信用交付属于后续可选扩展，需要分别结算 DeliveryLeg 和未清偿义务。第一版不以一笔“瞬时远程结算”掩盖运输风险。

### 6.3 必守条件

- 每份货物有唯一账本位置，移动不复制数量。
- 预留数量不可被第二笔交易再次使用；取消释放的只是仍有效的预留。
- 所有者与保管人分离，保管人死亡不自动销毁或转移所有权。
- 损坏、消耗、生产和自然掉落必须有来源事件；不要求整个生产世界的物资总数永远不变。
- 失败不自动退款已实际丢失的货物，补偿需要另一笔真实转移。
- 结算键防止同一交付事件重复执行；存档恢复也不得二次发放。
- 生命值遵守已有伤害与治疗规则，不作为物资守恒项相加。

## 7. 权限、共同任务与领导更替

### 7.1 有限授权

授权至少限定操作类型、资源账户、单次上限、累计上限或有效期。命名为首领不直接开放全部仓库。对私人物资的操作需要产权人同意或已有授权。

普通成员的工作请求与高风险行动提议共用“条款—回应—承诺—执行”链。已接受任务在条件稳定时持续，不每轮重新投票。失去授权影响尚未执行的越权动作；已经结算的事实不回滚。

### 7.2 PROVISIONAL 原型组织规则档案

以下只是新测试夹具的建议配置，未写入任何现有参数：

| 项目 | 测试约定 |
|---|---|
| 日常事务 | 按已接受的分工与资源限额执行 |
| 重大提议资格 | 提议发出时的有效成员名单快照 |
| 通过条件 | 支持数严格超过资格名单的一半 |
| 消息未送达/未回复 | 不算同意，不由系统代投 |
| 表决截止 | 使用明确模拟时间；长度在夹具中配置 |
| 平票或未达门槛 | 维持原权限，保留异议记录 |
| 无人在位的必要事务 | 只使用预先约定的临时保管/维护权限 |
| 亲自参加危险任务 | 即使组织批准，仍需个人接受任务范围 |
| 更替冷却与重复提议 | 版本化配置，禁止每 tick 重复罢免 |

更替提议必须包含目标职位和候选持有人，不接受“系统挑一个最受欢迎的人自动上位”。名义任职和实际支持分别记录。测试此规则不意味着所有未来组织都必须使用多数表决。

### 7.3 事务性转移

有效更替按一个规则事务撤销旧授权、授予新授权、记录职位变化，并更新可操作界面。公共合同由组织承担时继续存在；私人担保仍由对应主体承担。

保留失位者的实体 ID、位置、健康、记忆、私人所有权和人际关系。驱逐、没收或攻击要通过额外行动结算。不得以“失位”统一清空全部访问之外的个人数据。

## 8. 认知、记忆和关系更新

每次学习输入首先来自直接感知或被送达的转述。记忆包含来源、原始事件引用、信息通道、获得时间、显著度、完整度及记忆层。数据库存在 `source_event` 不代表 NPC 可以越权读取原始事实。

处理顺序：收集合法感知 → 区分事实片段与人物解释 → 更新信念证据 → 形成或合并记忆 → 生成有来源的关系变化 → 下一次决策检索相关摘要。

关系投影需要幂等键，例如“观察者＋原始证据族＋更新规则版本”。同一传闻绕一圈回来不能当新事件再次增加怨恨；真正独立的新证据可以更新置信度或修正归因。更正不删除旧账，而追加信念修订记录。

正式债务/担保放 Commitment 或协议账本；`obligation` 是主体感受到的人情义务，不能替代可结算的欠货数量。`belong` 的实际方向与含义必须遵循既有实现，不擅自变成全局部落忠诚度。

严重事件不必对所有人产生同样变化。某人看到救援可增加信任，另一人只知道分给自己的物资减少；未知事实不能作为关系更新的理由。

## 9. 派系识别与组织成立

首先记录可观察的共同提议、相互担保、共享任务和资源安排。用这些记录形成候选合作群，而不是直接根据关系矩阵聚类后强制加入。

第一版正式形成派系需要：可执行共同主张、至少两个实际接受加入的主体、至少一项有效共同承诺，并能引用反复协作的记录。反复次数和观察窗口作为 PROVISIONAL 配置，建议测试夹具使用“窗口内三次独立共同活动”；不得把这一数字当真实社会定律。

状态可为 candidate / informal / active / dormant / dissolved。名称、代表与公开宣告为可选行动。外部未获知组织时仍可存在；对外认知由 Perception/Belief 单独演化。

退出或分裂更新成员记录和财物安排，不删除组织历史。外部观察者可能仍持有过时成员名单；不能同步广播退出事实。

## 10. 有限冲突与修复执行器

复用已验收的移动、伤害和救援系统。JointOperation 增加具体目标、授权、参加者、资源预算和退出条件，不新增全图敌对的强制决策入口。

执行前验证：目标已被行动方获知、参加者有效、可到达、补给可用。行动中按个体能知道的变化重新判断；停止条件优先于扩大戏剧性。

Grievance 记录“谁指控谁、依据什么、要求什么”。事实伤亡、责任判断和组织授权三者分离。集体关系变化仍通过个体获知和归因，不从一个伤害事件对所有组织成员批量扣分。

修复协议包含有效接受人、权限范围、物资或行为条款、期限和已履行部分。返还要实际转移；停战不能替未授权团体承诺。履约后追加新的合作证据，旧事件保留。

## 11. 决策运行时与未来模型边界

```text
合法感知与自身状态
→ 相关记忆和已知承诺
→ 当前需求与已知协作机会
→ 候选行动 / 可提出的任务
→ Intelligence Provider 选择意图
→ WorldCore 重验前置条件
→ 执行并记录事实
→ 分发不同的感知投影
```

候选行动生成不能因为读取全局隐藏事实而泄露信息。例如不知道另一营地缺药时，不应凭空给出“利用对方缺药抬价”的选项。

规则版使用固定规则版本和可记录的选择依据。未来模型只能读取相同受限视图；返回意图后同样校验授权、资源、参与者和截止时间。超时、非法动作或过期结果回到已有安全行为，不冻结世界或凭空补全操作。

慢速的集体商议和任务调整与移动/战斗 tick 分开。已接受的长期任务由执行器持续运行，不每帧调用决策器。模型升级需单独评估，首版不实际调用。

## 12. 存档、重放和 Python/Godot 一致性

新字段以实际 schema 审计后批准的版本加入。旧存档缺少多部落对象时初始化为空或明确标记的默认状态，不伪造以往贸易和战争。背景设定与模拟历史有不同来源类型。

保存对象至少包含未完成提议、成员资格快照、回应、有效授权、预留、货物位置、交付状态、任务进度、消息队列、事件序号、关系与记忆来源、随机状态和规则配置版本。

历史队列完整保留，HUD 的短 `events` 可裁剪；不能以清理 HUD 为由删社会历史。较大规模若需分段归档，保持引用可解析，本轮不改变现有存档策略。

所有截止时间和延迟按模拟时间，而非真实墙钟。相同输入、种子、规则版本和执行顺序应产生相同权威状态；需明确两语言共享的随机算法、事件排序及数值表示，不能假设相同 seed 的内置 RNG 自动一致。

关系小数误差可使用统一定点单位或明确舍入规范，但必须在审计后选择并迁移，不在文档阶段擅改旧值。parity 对比 ID、状态、账本、知识权限和行为结果，动画帧率不作为逻辑一致性依据。

并发请求基于版本化快照；提交时逐项重验，按稳定顺序解决资源竞争。同一最后一份物资不能被两个行动消费。模型晚到、取消和读档都要走同一幂等保护。

## 13. 验收清单

下表是待执行测试，不表示通过。使用测试夹具可以构造前提；原生 GUI 验收不得通过调试注入库存、关系、授权或事件替代实际流程。

| ID | 场景 | 必须看到的结果 |
|---|---|---|
| T01 | 同一个人属于营地、家族、部落和派系 | 各关系分离，不能一个字段互相覆盖 |

## 14. 如何验证因果，而不是只看一段好故事

规则测试可从同一快照分两支，仅改变一个允许的行动，例如“返回搜救”与“直接返营”，比较交付、知识、关系和下次选择。记录所有其他输入、种子和版本。

另做反事实排除：不给观察者传递相关消息，观察其判断是否保持原状；保留一切但移除同一证据的重复投递，确认没有不合理增益。这些是调试测试，不在正常游玩中偷偷修改世界。

对某类历史没有产生预期变化时，记录原因；不能补写台词冒充真实策略变化。可解释不等于能证明模型内部心理，只能核对可记录输入、规则、输出和后果。

## 15. 原生试玩路线

**路线 A：和平贸易。** 正常获得食物和工具，认识邻营，提出并履行交易，回营分配收益，再观察第二次任务参与者。

**路线 B：风险与修复。** 通过正常移动、运输和既有危险机制遇到延误或伤员，选择搜救/返还/解释，检查消息与关系。不保证每个 seed 都生成同样事故。

**路线 C：失位后继续生活。** 使用公开的提议和回应机制形成持续分歧，在条件满足时发生更替，玩家以普通成员继续完成一次工作或交易。测试夹具可以设置初始分歧，但 GUI 路线不得直接写入罢免结果。

**路线 D：有限冲突。** 从可追溯争议到有效动员，完成一次有目标的行动并停止；另跑和平处理对照。完整交战不作为两营基础贸易的先决条件。

## 16. 交付证据格式

每次实施提交至少包含：工作包 ID、基线 SHA、实际修改清单、受保护路径核对、字段/规则差异、PROVISIONAL 参数变化、资产准入记录、测试命令与结果、parity 差异、存档迁移、种子、Godot 版本、GUI 操作路径及录像/截图位置、剩余风险、提交 SHA。

未运行的项目填写“未运行及原因”，不能填通过。设计文档完成、代码提交、逻辑测试通过、引擎导入通过、真人可玩验收分别更新状态。
