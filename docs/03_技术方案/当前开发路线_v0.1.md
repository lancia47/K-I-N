# 部落求生：生存底座 → 多物种生态 → KIN 社会因果执行计划

**版本：v0.1｜开发执行基线**  
**定位：从现有 campaign 生存玩法，逐步扩展到多物种生态，再接入 KIN 社会因果层**  
**上游设计：[`KIN_Game_Project_Design_v0.5.md`](../KIN_Game_Project_Design_v0.5.md)**

> 本文不是新的“设计哲学”，而是当前项目的**开发执行基线**。  
> 核心原则：先让生存与生态成为真实、可保存、可回归的 WorldCore，再把这些真实事件社会化；第一版不依赖在线模型。

---

## 阶段 0：冻结现有项目边界

先做只读基线，不修改项目文件：

- 记录当前分支、工作区脏文件、未跟踪资产和现有用户改动；
- 将 `proto_h01/` 的当前 campaign 作为主工作区；
- 保留旧短局模式、`godot_ai`、`tools` 和已有资产；
- 确认当前 Python campaign 规则、GDScript 镜像、存档 schema、测试入口和 Godot 版本；
- 建立本阶段允许修改的文件清单。

本阶段的输出是**基线清单和变更边界**，不提交玩法代码。

---

## 阶段 1：CC0 动物资产供应链

首批目标是 8 种野外生态动物：

```text
鹿、狼、狐、野猪、兔、鱼、鸟、熊或同等级大型危险兽
```

执行内容：

- 优先检查现有 Quaternius CC0 管线能否覆盖物种；
- 缺失物种从其他 CC0 来源逐个审计；
- 每个候选文件记录来源、许可、作者、版本、SHA256、格式、骨骼和动画；
- 检查 idle、移动、攻击/逃跑、受击/死亡等动作覆盖；
- 检查比例、材质、碰撞、镜头可读性和 Godot 导入；
- 生成正式资产 manifest 和候选替代清单；
- 对精确包执行 vendor admission dry-run。

资产复制和正式纳入必须经过游戏资产 vendoring 技能规定的准入确认；**资产来源验证、项目接入、引擎导入和视觉验收分别报告，不能互相替代。**

---

## 阶段 2：数据驱动的生态契约

在资产准入结果确定后，扩展现有 `deer/wolf` 硬编码结构。

每种动物定义：

```text
species_id
habitat
needs
movement_profile
perception_profile
threat_response
interaction_targets
combat_or_escape_profile
resource_result
observable_cues
asset_action_profile
```

存档和快照改为接受物种目录中的合法 `species_id`，不再把 `deer` 和 `wolf` 写死在验证器中。

首批只做可玩生态闭环：

- 栖息区域；
- 移动和日常状态；
- 觅食或捕食；
- 攻击、逃跑、警戒或区域回避；
- 与其他动物的至少一种互动；
- 狩猎、受伤、死亡和掉落；
- 可观察声音、轨迹、姿态或环境反馈；
- 存档恢复和 Python/Godot parity。

第一阶段明确**不加入**：

- 繁殖；
- 幼体；
- 季节种群；
- 遗传；
- 疾病；
- 长期承载量。

---

## 阶段 3：生存与生态整合

保持现有 campaign 的生存开局：

```text
空手取材
→ 制作工具与火源
→ 狩猎 / 捕鱼 / 采集
→ 处理或烹饪食物
→ 遭遇动物危险
→ 返回营地
→ 治疗、救援、分配和恢复
```

新增或统一以下事件：

- `animal_sighted`
- `animal_tracked`
- `animal_hurt`
- `animal_killed`
- `predator_encounter`
- `warning_given`
- `member_aided`
- `member_abandoned`
- `carried_wounded`
- `meat_shared`
- `resource_claimed`
- `animal_carcass_used`

每个事件必须进入现有事件系统，并为后续社会因果层保留：

```text
参与者
目标
位置
可观察结果
直接目击者
资源变化
动物状态变化
```

NPC 需要能够：

- 识别危险动物；
- 追踪或放弃追踪；
- 警告成员；
- 避开或引诱动物；
- 救援、搬运和照料伤员；
- 参与狩猎；
- 对肉、皮革、药材和工具进行分配。

---

## 阶段 4：生存验收门

社会关系实现前，必须先通过生存与生态门禁：

- 玩家能独立获得至少一种可持续食物；
- 至少两种动物会对玩家行为产生不同反应；
- 至少一次狩猎产生血迹、尸体、路线或危险后果；
- 至少一次动物危险触发警告、撤退、救援或搬运；
- 动物掉落不会重复生成；
- 资源、生命、背包和营地库存守恒；
- 固定种子和随机种子都没有永久软锁；
- Python 与 Godot 状态一致；
- 保存后重新启动，动物、资源、伤势和营地状态保持一致；
- 至少一条无状态注入的 Godot 原生路线跑通。

> **门禁规则：** 如果本阶段不成立，暂停社会因果实现，回到生态或生存规则修复。

---

## 阶段 5：生态事件社会化

在生存门禁通过后，接入 KIN 社会因果层。

历史保存方式：

- `history`：存档中的追加式完整历史；
- `events`：现有短事件队列，继续服务 HUD 和即时表现；
- `perceptions`：主体通过直接观察或转述得到的内容；
- `beliefs`：主体的判断、置信度和来源链；
- `memories`：带 `source_event`、`source_type`、`salience` 和 `layer`；
- `relationship`：保留 `trust/fear/belong`，增加 `obligation/resentment/familiarity`。

第一批关系来源不是借粮，而是：

```text
共同狩猎
→ 危险中的警告或救援
→ 伤员搬运
→ 狩猎成果分配
→ 成员记住谁帮助过自己
→ 下一次狩猎、求助和分工发生变化
```

食物请求作为生存压力下的后续社会事件接入，而不是首个孤立 Demo。

**第一版不接入在线模型。** NPC 继续使用确定性规则，预留 `Intelligence Provider` 接口供未来模型调用。

---

## 阶段 6：社会因果验收

必须验证：

- 直接目击者和未在场主体看到的信息不同；
- 目击者不能读取私有库存和隐藏目标；
- 二手传播保留来源链并产生信息损失；
- 救援、抛弃、分配和违约会改变关系；
- 同一动物事件对不同主体产生不同记忆；
- 下一次狩猎、求助、分工或交易会受到既有经历影响；
- 历史、记忆、belief 和关系在保存/恢复后保持一致；
- Godot 与 Python 的历史事件、认知结果和关系变化保持 parity；
- 玩家能通过世界线索和近期原因理解关键关系变化，不显示完整社会图。

---

## 阶段 7：资产、生态和社会的联合试玩

最后运行三类路线：

1. **生存路线**：空手到工具、火源、食物和营地；
2. **生态路线**：追踪、狩猎、遭遇危险、撤退或救援；
3. **社会路线**：共同狩猎、救援/抛弃、资源分配、关系变化和下一次选择。

每阶段交付：

- 修改文件清单；
- 规则和数据契约变化；
- 资产来源和哈希；
- Python 测试结果；
- Godot headless 结果；
- Python/Godot parity；
- 存档迁移结果；
- 固定种子与随机种子差异；
- GUI 实际路径；
- 未完成项与风险；
- 是否改变 `PROVISIONAL` 参数；
- 提交哈希。

当前工作区的用户改动必须保留。未经明确准入，不覆盖：

- `godot_ai`
- `tools`
- 现有资产
- 旧短局回归路径

# 基线状态总结

这条路线的顺序必须保持：

```text
冻结边界
→ 资产准入
→ 数据驱动生态
→ 生存/生态闭环
→ 生存验收门
→ 真实生态事件进入 History
→ Perception / Belief / Memory / Relationship
→ 社会因果验收
→ 联合试玩
```

它与 K-I-N v0.5 的对应关系是：

```text
WorldCore 先成立
→ 事件具有真实后果
→ 事件才有资格成为社会历史
→ 历史才能塑造 Memory / Belief / Relationship
→ 关系才能反过来改变下一次选择
```

因此，本基线的核心判断是：

> **社会因果不能建立在“文本发生了什么”之上，而必须建立在已经通过生存与生态规则真实结算过的事件之上。**
